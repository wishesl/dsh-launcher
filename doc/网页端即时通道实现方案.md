# 网页端即时通道实现方案（内嵌视图门禁）

> 状态：已实现（插件 0.2.13）
> 涉及：`dsh-launcher/embed/dsh-launcher-plugin/lib/client.js`（唯一行为改动点）、插件 `package.json` / `README.md`、`AGENTS.md` §9.6
> 启动器 Go / 前端 / 桥接协议：**零改动**

## 0. 一句话

网页端即时通道（page 角色）**只让启动器内嵌视图那一个页面接入**，外部标签页不接入；主题对这些页面照旧靠服务端插件写盘 + DSH 广播同步（实测约 300ms）。

## 1. 现象

多开 DSH 网页（内嵌视图 + 外部浏览器标签）时，右栏「运行日志」里 `网页端已接入主题即时通道` 以**每秒 2 条**的节奏无限刷；网页端「设置 → 启动器」面板里的「链接状态 / 网页通道」跟着一亮一灭，即用户反馈的"一直闪烁重连"。

## 2. 证据（真机 `%APPDATA%\DSHLauncher\logs\app.log`）

同一实例 `713daeb17686`，两段：

| 时段 | 时长 | `已接入` 行数 | 每秒接入 | 段内 `已断开` |
|---|---|---|---|---|
| 17:13:39–17:23 | ~10 分钟 | ~1225 | 593 秒恰好 2 次、28 秒 1 次 | **0** |
| 23:07:50–23:16:45（仍在跑） | ~9 分钟 | ~1077 | 稳定 2 次 | **0** |

三条指纹：

1. **稳定 2 次/秒**，不是退避爬升后的稀疏重试。全库 44 条 `已断开` 分布在历史各处（都是真的关页面），两段振荡期内**一条都没有**。
2. 振荡开始时，第二条 `已接入` 到来**之前没有 `已断开`** —— 即"第一条还连着，第二个页面就接进来了"。正常单页面的样子是 17:38:09 接入 → 17:39:48 断开 → 17:40:16 接入 → 21:24:17 断开，中间静默几小时。
3. **被踢那条是静默的**：`unregister` 判 `b.pages[id] == c` 才记断开，而踢人时 `pages[id]` 已被新连接覆盖 —— 所以日志里只剩"一直有新页面接入"，看不出"启动器一直在踢人"。这是它长期没被发现的原因。

## 3. 根因

| # | 位置 | 做了什么 |
|---|---|---|
| 1 | `launcher_bridge.go` `pages map[string]*bridgeClient` | 键是 instanceID，**结构上只容得下一个页面** |
| 2 | `handlePageHello`：`b.pages[id] = c` 后 `prev.conn.Close()` | 新页面接入即踢掉旧的 |
| 3 | `client.js` `ws.onclose` → `scheduleRetry()` | 任何断开都要重连，**没有"被主动踢"这个语义** |
| 4 | `client.js`：延时取 `RETRY_DELAYS_MS[retryIdx]`，而 `onopen` 里 `retryIdx = 0` | 踢人只发生在握手成功之后 → 退避永远停在 500ms |

⇒ 页面 A 接入踢 B → B 500ms 后接入踢 A → A 500ms 后接入踢 B…… **无阻尼的自激振荡**，正好 2 次/秒。

**这是设计层面的漏洞，不是偶发 bug**：启动器把"客户端自己发起、条数由客户端决定"的通道（网页端半边跑在浏览器里，坐标由 `webserver/index-inject` 注入到**每一次页面加载**），当成了"启动器自己拥有、条数恒为 1"的资源。plugin 通道可以这么管（服务端半边自己就是单例：模块级一个 socket，新装载会话先关旧连接再连），page 通道不行。

## 4. 设计模型

- **plugin 通道 = 权威**：每实例进程一条，读/写主题、自重启、能力上报都在它上面。
- **page 通道 = 内嵌视图专用的旁路**：它存在的唯一理由是"省掉等写盘落地的 330–350ms"（页面自己的 `theme.setTheme()` 是本地优先：先重绘、写盘丢后台）。
- 因此它天生是**每页一条**、且**只对启动器自己那个页面有意义**：用户点启动器主题按钮时，看的就是内嵌视图。外部标签页晚 300ms 跟随完全可接受。

## 5. 门禁

### 5.1 为什么不能用 URL 标记

最初方案是"启动器给内嵌 iframe 的 URL 加个标记（`?dshl=embed`），page 层检查 `location.search`"。实测否决：

| 请求 | 结果 |
|---|---|
| 内嵌那条（带 token）`http://127.0.0.1:3080/?token=…` | **`303 See Other` → `location: ./`** —— token 被换成会话，**query 被整个丢掉** |
| 外部打开那条（`service.url`，不带 token）`http://127.0.0.1:3080/` | `401`（浏览器里有会话 cookie 才通），落地同样是 `/` |

⇒ 内嵌页与外部页**落地 URL 完全相同**，`location.search` 是空的，URL 上任何标记都活不到页面里。

（`webserver/index-inject(table)` 钩子也拿不到请求上下文，所以服务端半边**无法**按请求区分内嵌/外部，只能在注入里给所有页面同一份坐标。）

### 5.2 实际采用：本页是否被内嵌

```js
window.self !== window.top
```

- 启动器的内嵌视图就是前端里的 `<iframe src={embedUrl}>`（`App.tsx`），外部标签页是顶层窗口 → 这个判断的语义**正好**是"内嵌视图"。
- **零启动器改动**，且不受 303 重定向影响。
- 读不到 `window.top` 或比较抛异常 → **一律当作"不是内嵌"**（不连是安全方向：主题仍会同步，只是走服务端写入那条慢路）。

### 5.3 门禁之后，启动器的单槽重新正确

单槽 + 踢旧之所以出事，是因为**第 2 个页面会来抢槽**。门禁之后"一个实例同时只有内嵌视图这一条 page 连接"从**启动器硬凑的假设**变成**真命题** —— 所以 Go 侧一行不改。

## 6. 已知边角（**不是 bug**，按约定只备注不额外防护）

- 同一条内嵌 URL / 同一个页面出现多条连接（操作失误、或同一页里客户端半边被装载两次）→ 仍然互踢。**接受**：正常使用不会出现，且只发生在"同一个 URL 被开了多次"这种操作失误场景。
- **不额外加防护**：不加"已有连接就拒绝新连接"——iframe 刷新时新连接可能比旧的 unregister 先到，那样内嵌页会被自己的刷新拒掉、客户端 `disabled=true` 后再也不连，主题静默退回慢路。
- 这**不是安全边界**（token 本来就注入到每个页面），只是接线纪律；真正的边界仍是 Origin 白名单 + token + launch 校验。

## 7. 测试与验收

测试（每条都做反向验证）：

1. `testdata/plugin-client-harness.mjs` 补假 window 的 `self` / `top`（顶层 = 同一对象；内嵌 = 不同对象）；原有端到端用例改成内嵌模式。
2. 新增用例「顶层页面不接入」：断言**不发 `page-hello`**、桥接侧 `hasPage` 始终 false。
3. Go `TestBridgePageChannelSkipsTopLevelPage`：用真 `lib/client.js` 跑该用例，断言无连接。
4. 反向验证：去掉 `isEmbeddedView()` 门禁 → 测试 3 必须失败；把假 window 的 `self`/`top` 换成同一对象 → 测试 3 必须失败。

真机验收：

| # | 判据 |
|---|---|
| 1 | 「内嵌视图 + 2 个外部标签页」跑 10 分钟，`已接入` 只有内嵌页那一条，不随外部标签页增长，无 2 次/秒重复 |
| 2 | 外部标签页 0 条接入记录；面板显示「未接入（本页不是内嵌打开的）」，不是红 |
| 3 | 内嵌视图里点主题按钮 → 当场换肤；每次点击只多 1 条 `已即时换肤` |

## 8. 不做的事

- 不改启动器 Go / 前端 / 桥接协议（单槽 + 踢旧保持原样）。
- 不加集合语义、不加连接上限、不做页面侧选举。
- 不删 page 通道的下行命令方向（内嵌页仍要"当场换肤"）。
- 不动客户端重连退避与"握手成功即清零"（启动器重启后快速恢复依赖它）。
