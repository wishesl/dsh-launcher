# 插件更新功能实现方案

> 目标：在现有插件市场（发现 / 已安装 / 收藏）之上，补上**「检查更新 → 单个更新」**闭环。
> 承接 `插件市场实现方案.md` §8 的 M3 里程碑（已装管理与更新检查），但把"更新检查"从一句话拆成可落地的设计。
>
> **本期范围（已拍板）**：M1 检查更新（只读）+ M2 单个更新。**不做批量更新**（已装插件通常只有几个，逐个点够用；
> 也因此右栏不需要 `[i/N]` 这类批量进度语义）—— 批量、github 自动判定、内置重装、降级回滚见 §12。
> 2026-08 现状核对：`market_ops.go` 已有 install/uninstall 单飞 + 流式日志 + 可取消，
> `market_installed.go` 已能读出 name/spec/version/kind/state/github，前端已装 Tab 已有行渲染骨架。
> **本方案零新增网络下载机制、零新增事件通道**，全部复用既有链路。

---

## 1. 结论先行（三句话）

1. **执行侧不用新做**：`dsh plugin --profile web <args>` 是 `pnpm` 的**薄转发**（已核对 `@deepseek-ai/dsh` 的
   `plugin-*.js`：init profile → `spawnSync("pnpm", args)` → `reconcilePlugins()`）。
   它的 reconcile 是**按安装后的实际状态**（谁声明了 `dsh.bundle` 就进层栈）而非按依赖 diff，
   注释里明确写了 "means `update` activates a package that gained its `dsh.bundle` declaration in a newer version"。
   → 更新就是 `dsh plugin … update <name>` / `add <name>@latest`，**官方 CLI 已经把更新这条路径设计好了**。
2. **难点只在"判断有没有更新 + 说清跨度"**：需要按 kind 分流（npm / github / linked / builtin），
   并把 semver 跨度（patch/minor/major/预发布）算出来给用户看，否则用户不敢点。
3. **风险控制复用现有契约**：实例运行中不许改文件（`requireStoppedInstance`）、全局单飞 `marketBusy`、
   15 分钟超时 + 可取消、进度进右栏「市场任务」标签。**不引入新事件**，只给 `MarketOpStatus` 加字段。

## 2. 现状盘点（本方案踩在上面的地基）

| 已有能力 | 位置 | 本方案怎么用 |
|---|---|---|
| 已装列表（name/spec/version/kind/state/github/description） | `market_installed.go: ListInstalledPlugins` | 直接作为更新的输入集合 |
| profile 依赖 spec（`^1.45.1` / `github:o/r` / `file:…`） | `readInstalledPlugins()` | semver 范围判定的依据 |
| 实际安装版本 | `readInstalledVersion()` 读 `node_modules/<name>/package.json` | "当前版本"的唯一可信来源 |
| CLI 调用构造 | `pluginCommand(inst, args…)` | 更新复用：`update <name>` / `add <name>@latest` |
| 流式执行 + 日志 + 取消 + 杀进程树 | `runMarketCommand()` + `winJob` | 原样复用 |
| 单飞互斥 | `marketBusy atomic.Bool` | 更新与安装互斥，天然复现 |
| 状态事件 | `dsh:market-status`（kind: install\|uninstall） | **扩 kind: update\|update-all + 加字段**，不新增事件名 |
| 目录白名单（entry url → install target） | `installTargetFor()` / `findRegistryEntry()` | 从已装 spec 反推更新 target，并在目录内校验 |
| 前端进度/自动弹右栏 | `MarketView.install()` + `openLogs('market')` | 更新走同一套 `stopIfRunning → onShowMarketLogs → api.xxx` |

**要补的缺口**：没有任何"latest 从哪来"的查询（`dsh_query.go` 只硬编码了 `@deepseek-ai/dsh` 一个包）。

## 3. 更新检测策略（核心设计）

按 `InstalledPlugin.Kind` 四条分流，**每条都能独立降级**，任何一条失败都不能让整个列表报错：

### 3.1 npm 类（主力路径，覆盖你本机 5/6 个插件）

- 取 spec 的 npm 名：`resolveNpmName(spec)` —— `^1.2.3` / `~1.2.3` / `1.x` / `1.2.3` / `latest` 都取 spec 里的包名，
  **不解析 spec 本身**，包名一律用 `InstalledPlugin.Name`（pnpm 写入的是真实包名，别名 spec 也已归一）。
- 查询最新版：**单包端点** `GET https://registry.npmjs.org/<name>`（**不要**用全量文档 `…/dsh` 那种，
  单包响应几十 KB，可用 `Accept: application/vnd.npm.install-v1+json` 进一步瘦身），读 `dist-tags.latest`。
- 镜像回退：沿用 `dsh_query.go` 的双源模式（官方 → `registry.npmmirror.com`），走 `a.proxyHTTPClient(15s)`。
- 判定：
  - `latest == installed` → 最新。
  - `installed < latest` → 有更新，再算**跨度**与**是否在 spec 范围内**。
  - `installed > latest`（本地装了预发布 / dist-tag 回退）→ 显示"本地版本高于线上"，**不提供更新按钮**。
- **预发布策略（决策 D2）**：npm `latest` 默认不指向预发布。若 installed 是 `1.3.0-rc.1` 而 latest 是 `1.2.9`，
  视为"本地更高"，不提示更新；只有用户显式点「切到 latest」才动。

### 3.2 github 类（`github:owner/repo[#path:/sub]`）

**本期不做自动判定**（决策 D10）：无法在不 clone 的情况下可靠得知远端是否有新提交，
未认证 GitHub API 限流 60 次/小时/IP 又会随插件数量增长而脆弱；误报"有新版"比不报更伤信任。

- 本期行为：kind=github 的行**不显示更新按钮**，只显示已有的 `github.com/owner/repo` 链接，
  外加一行灰字提示 `git 来源 · 请在目录页重新安装以拉取最新提交`（复用现成的安装路径）。
- 后端里保留 `readLockedCommit(spec)` 纯函数（解析 `pnpm-lock.yaml` 的 `codeload.github.com/<o>/<r>/tar.gz/<sha>`）
  并单测覆盖，供 M3 的自动判定直接使用 —— 只写不接，避免本期引入网络依赖。

### 3.3 linked 类（`file:` / `link:`，本地开发中）

- **永远不检查、永远不更新**：这就是用户正在改的源码（本机 `dsh-self-mcp` 就是这种）。
- 行内显示 `本地开发 · 不参与更新`，更新按钮不渲染。

### 3.4 内置类（launcher 内置 `dsh-self-mcp`）

**已实现重装动作**（原决策 D11「本期只做检测」已升级）：内置插件的"更新"本质是重新物化 + 重装，
现在直接复用 `InstallSelfRestartPlugin` 那条流程（解出内嵌源码 → 对
`file:<profile>/.dsh-builtin/dsh-self-mcp` 跑常规 pnpm 安装），`UpdatePlugin` 的 builtin 分支
委派给 `reinstallBuiltinSelfRestart`。

- 检测：launcher 内嵌源码版本（`embeddata.go`）vs profile 里已物化的
  `<profile>/.dsh-builtin/dsh-self-mcp/package.json` 版本，两者不一致即 `HasUpdate=true`、`Runnable=true`。
- UI：显示 `v0.1.0 → v0.2.1`，按钮为可点的「更新到 vX」（市场页内置面板与已装列表行都有）；
  内置面板在无更新时保留一个「重新安装」按钮（幂等覆盖，用于修「副本被改坏」）。
- **为什么必须能重装**：内置插件带 `relaxEmbedAuth`（放宽跨站内嵌的会话校验）。装过旧副本的用户
  若没有升级路径，内嵌视图会永久 401。⚠️ 插件版本号必须随能力变更一起 bump —— 否则新旧副本
  版本号相同，`pluginCopyMismatchReason` 分辨不出来，面板既误判又给不出「更新」按钮。
- 这是**唯一不依赖外网的更新检查**，实现成本极低。

## 4. 数据结构（Go）

```go
// market_update.go

// UpdateCheck 是"有没有新版"的判定结果，逐插件返回。
type UpdateCheck struct {
    Name      string `json:"name"`               // 包名
    Current   string `json:"current"`            // 已装版本（node_modules 实读）
    Latest    string `json:"latest"`             // npm dist-tags.latest / 内嵌内置插件版本
    Kind      string `json:"kind"`               // npm | github | linked | builtin
    HasUpdate bool   `json:"hasUpdate"`
    // Runnable=false 表示"本版本不能执行更新"（github / linked / builtin）——
    // 前端据此决定渲染"更新"按钮、"待支持"禁用按钮还是提示文案，不需要再判断 kind。
    Runnable  bool   `json:"runnable"`
    // Jump 是版本跨度：patch | minor | major | prerelease | downgrade | none | unknown
    Jump      string `json:"jump"`
    // InRange=true 表示落在 spec 声明范围内（pnpm update 即可）；false 表示需改 spec（pnpm add @latest）
    InRange   bool   `json:"inRange"`
    // Risky=true 需要二次确认（major / 预发布 / spec 形状不可判定 / 超范围）
    Risky     bool   `json:"risky"`
    // Target 是更新时要写回的命令行 target（服务端推导并过白名单；前端不参与）
    Target    string `json:"target"`
    // Remote 是远端标识，供 UI 显示（npm 包名 / owner/repo）
    Remote    string `json:"remote"`
    // Err 非空 = 该项检查失败（只影响这一行；不阻断其他行）
    Err       string `json:"err"`
}

// UpdateCheckResult 是整批结果 + 汇总
type UpdateCheckResult struct {
    Checked   string        `json:"checked"`   // RFC3339，检查时间
    Plugins   []UpdateCheck `json:"plugins"`   // 按包名排序（行序稳定，不随检查抖动）
    Updatable int           `json:"updatable"` // HasUpdate && Runnable 计数
}
```

`MarketOpStatus` 增量字段（**不新增事件**，保持单一所有者原则）：

```go
type MarketOpStatus struct {
    State   string `json:"state"`   // running | done | failed | cancelled
    Kind    string `json:"kind"`    // + update | update-all
    Target  string `json:"target"`
    // 新增（可选，空则前端不显示）
    Name    string `json:"name,omitempty"`    // 当前正在更新的插件名
    From    string `json:"from,omitempty"`    // 版本跨度展示
    To      string `json:"to,omitempty"`
    Error   string `json:"error,omitempty"`
    Blocked []string `json:"blockedBuilds,omitempty"`
}
```

`MarketOpResult` 复用（不新增字段）：单个更新时 `Installed` 字段承载"本次实际更新的包名"，
语义上它就是"变更清单"，与安装一致。

## 5. semver 与范围判定（纯函数，可单测）

现有 `util.go` 只有 `parseVersion`（正则校验 x.y.z[-pre]），**没有比较能力**，必须补：

```go
// compareSemver(a, b string) int   // -1 / 0 / 1，预发布按 semver 规则排序（无 pre > 有 pre）
// jumpType(cur, next string) string // none|patch|minor|major|prerelease|downgrade
// inRange(cur string, spec string) (bool, bool) // (是否在范围内, 是否可判定)
```

- `inRange` 只支持 npm 常见范围：`^`、`~`、`>=`、`1.x`/`1.*`、精确版本、`latest`/`*`。
  **不支持的不猜测**：返回 `(false,false)` → UI 按"需确认"处理，走 `add @latest` 重写 spec。
- 判定优先级：`!inRange` → Risky；`jump==major` → Risky；`jump==prerelease` → Risky（默认不允许自动降到 pre）。
- 非 npm spec（`file:`/`workspace:`/`git+`/别名）→ `(false,false)`，kind 决定后续动作。

**测试要点**（`market_update_test.go`，沿用表驱动风格）：

| 用例 | 期望 |
|---|---|
| `1.2.3 < 1.10.0` | -1（字符串比较会错，必须有此用例） |
| `1.2.3 < 1.2.3-rc.1` | 1（无 pre 更大） |
| `1.2.3-rc.1 < 1.2.3-rc.2` | -1 |
| spec `^1.2.3` vs latest `1.3.0` | inRange=true, jump=minor |
| spec `^1.2.3` vs latest `2.0.0` | inRange=false, risky=true |
| spec `~1.2.3` vs `1.3.0` | inRange=false |
| spec `file:…` / `github:o/r` | 可判定=false |
| lock 解析：含 `codeload.github.com/o/r/tar.gz/<sha>` | 提取到 sha |
| lock 解析：文件缺失/无匹配 | 空结果，不 panic |

## 6. 后端接口（Wails 绑定，2 个新方法）

```go
// 检查更新：并发拉取（8 并发 + 15s 超时 + 双 registry 回退），单项失败只标 Err
func (a *App) CheckPluginUpdates(force bool) (*UpdateCheckResult, error)

// 单个更新：重校验 → 停实例守卫 → update / add @latest → 流式日志
func (a *App) UpdatePlugin(instanceID, name string, allowRisky bool) (*MarketOpResult, error)
```

实现要点：

1. **缓存**：`UpdateCheckResult` 内存缓存 + 5 分钟 TTL。
   `force=true` 忽略 TTL（对应 UI「检查更新」）。插件更新检查是纯读，缓存窗口内切 Tab 不重复打网络。
2. **并发**：`sync.WaitGroup` + `chan struct{}` 信号量限 8 并发；结果按包名排序输出（稳定 UI，避免每次检查行序跳动）。
3. **命令分流**（这是唯一需要判断的地方）：

   | 情形 | 命令 |
   |---|---|
   | npm，InRange=true | `plugin --profile web update <name>`（不动 spec，锁文件内升级） |
   | npm，InRange=false 且 allowRisky | `plugin --profile web add <name>@latest`（重写 spec 为 `^x.y.z`） |
   | github / builtin | **本期拒绝**，返回明确提示（走目录页重新安装 / M3 支持） |
   | linked | **拒绝**：`本地开发插件不支持自动更新` |

4. **target 安全**：`UpdatePlugin` 收到的 `name` 必须**先命中已装集合**（`readInstalledPlugins`），
   再推导 target，最后过 `targetRe` 白名单 —— 与安装同级别的服务端校验，前端只传名字，永不传 target。
5. **实例守卫**：复用 `preflightMarketOp(instanceID)`（运行中拒绝 + 版本可用性校验），
   前端 `stopIfRunning()` 引导"停止 → 更新 → 拉起"，与安装路径完全一致。
6. **超时/取消**：沿用 `marketOpTimeout=15min` + `CancelMarketOp()`，单个更新同样可取消；
   进度上报 `Name/From/To`，右栏显示「正在更新 dsh-review v0.1.1 → v0.1.4」。

## 7. 前端设计（React + TS）

**布局铁律遵守**：所有进度输出进**右侧常驻第三栏**的「市场任务」标签，不做浮层。

### 7.1 发现页（`market === 'discover'`）

- 顶部工具条右侧增加一个状态胶囊：`可更新 2`（点一下切到已安装页）／`全部最新`（灰）／检查中不显示。
- 已装插件卡片：`已安装` 徽标旁加 `可更新 → v1.3.0`（accent 色，点击切到已安装页）。
  **发现页不直接提供更新按钮**（避免把"改环境"的动作放在浏览流里）。

### 7.2 已安装页（主战场）

```
┌────────────────────────────────────────────────────────────────────────┐
│ 已装 6 个 · 2 个可更新                              [检查更新]           │  ← 汇总条
├────────────────────────────────────────────────────────────────────────┤
│ dsh-dream-skin   v8.30.1 → v8.31.0   [minor]      [更新] [☆] [开关] [卸载]│
│ dsh-review       v0.1.1  → v0.1.4    [patch]      [更新] …              │
│ @michengai/…     v0.1.32 → v1.0.0    [⚠ major]    [更新…] …             │  ← 需确认
│ dshmarket        v1.45.1 (最新)                    [☆] [开关] [卸载]     │
│ dsh-self-mcp     内置 v0.1.0 → v0.1.1              [M3 支持] …          │
│ some-local-pkg   本地开发 · 不参与更新                                   │
└────────────────────────────────────────────────────────────────────────┘
```

- **行内元素**（在现有 `.installed-row` 的 head 行追加，不新造卡片）：
  - 版本跨度：当前版本（灰 mono）+ `→` + 目标版本（accent mono）。
  - 跨度徽标 pill：`patch`（灰）/`minor`（蓝）/`⚠ major`（黄 tag-warn）/`builtin`（灰）。
  - 主操作按钮：`更新`（`btn-primary btn-sm`）；Risky 时文案 `更新…` 并弹确认。
  - 状态：`检查中…`（转圈/骨架）、`检查失败 · 重试`（`Err` 非空时行内小字，**不弹 toast 刷屏**）。
- **汇总条**：`可更新 N` + `检查更新`（force）。**本期不做「全部更新」**。
- **确认弹窗**（复用现有 `.modal` 模式，轻量，不引组件库）：
  - major：`@michengai/… 0.1.32 → 1.0.0 是主版本升级，可能包含不兼容变更。` + 「仍要更新」
  - 范围外（spec 是精确版本 / `~` 之类）：`该插件的 spec 为 1.2.3，更新将把它改写为 ^1.4.0。` + 「仍要更新」
  - **不提供"以后不再询问"**（更新是偶发动作，且每次都改用户环境）。
- **动作流**（与 `install()` 完全同构，直接复制该函数形态）：

```
点击更新 → stopIfRunning()（实例运行中则确认停止）
        → onClearMarketLogs() + onShowMarketLogs()（右栏切"市场任务"）
        → setBusy(true) → api.updatePlugin(targetId, name, allowRisky)
        → 成功：toast「已更新 X v1.0.0 → v1.1.0，重启实例后生效」＋ wasRunning 则自动拉起
        → 失败/取消/构建脚本被拦：复用现有 pendingApprove 放行重试机制
        → finally: busy=false + loadInstalled() + checkUpdates(false)
```

### 7.3 右栏「市场任务」标签

- 现有 `LogDrawer` 的市场任务面板**不改结构**，仅消费新增的 `name/from/to` 字段：
  `正在更新 dsh-review v0.1.1 → v0.1.4 …`，完成后 `更新完成，重启实例后生效`。
- `MarketOpState`（App 的 `marketOp`）接受新 kind `update`（`types.ts` 注释与 App 的映射同步）。

### 7.4 api.ts / types.ts

```ts
// api.ts
checkPluginUpdates: (force: boolean): Promise<UpdateCheckResult> => CheckPluginUpdates(force),
updatePlugin: (instanceId: string, name: string, allowRisky: boolean): Promise<MarketOpResult> =>
  UpdatePlugin(instanceId, name, allowRisky),
// types.ts：UpdateCheck / UpdateCheckResult；MarketStatusEvent 增补 name/from/to
```

## 8. 关键决策表

| # | 决策 | 理由 |
|---|---|---|
| D1 | 更新执行 = `dsh plugin … update`/`add`，**不自己调 pnpm** | 官方 CLI 已内建 bundles 层栈 reconcile（"update activates a package that gained dsh.bundle"）；与实例运行版本一致 |
| D2 | npm 只跟 `dist-tags.latest`，**不自动降/升到预发布** | 插件生态 latest 才是稳定面；预发布抖动会让用户天天看到"可更新" |
| D3 | 检查结果**缓存 5 分钟**，手动「检查更新」强制刷新 | 切 Tab 不打网络；但用户主动点必须真查（与目录 force 语义一致） |
| D4 | 复用 `dsh:market-status` + 扩 `kind: update`，**不新增事件名** | AGENTS.md §4.1「事件订阅单一所有者」；新增事件要动 App 的订阅装配，收益为零 |
| D5 | `major`/范围外/预发布一律 Risky，**必须二次确认** | 更新是"改用户环境"的动作，误点成本高于多点一次 |
| D6 | linked 与 inbox 官方包**不可更新**（不渲染按钮，服务端也拒绝） | 与卸载/开关的既有保护一致 |
| D7 | **不做自动更新 / 后台静默更新** | 插件变更需重启实例才生效，静默更新会让"重启才生效"变成惊吓 |
| D8 | **不做批量更新，不做 github 自动判定**（本期范围决定） | 已装插件数量小，逐个点够用；github 判定需要额外网络依赖与限流处理，误报代价高 |
| D9 | 不做 github 自动判定的同时，**仍写入 lock 解析纯函数 + 单测**（只写不接） | M3 接自动判定时不用重做解析；纯函数零副作用，不增加本期运行期风险 |

## 9. 边界与失败处理

| 场景 | 行为 |
|---|---|
| npm registry 不可达（整体断网） | 每行 `检查失败 · 重试`，汇总条显示"检查失败 1"。**不抛全局错误、不清空已装列表** |
| 目录（awesome-dsh-plugin）不可达 | **不影响 npm 检查**（npm 检查只依赖 registry）；仅在需要目录反推 target 时降级为 spec 反推 |
| 插件从 npm 下架（404） | `Err="包已下架或不可访问"`，行内提示"建议卸载"，**不给更新按钮** |
| 用户 pin 了精确版本（`"1.2.3"`） | InRange 只在 latest==1.2.3 时成立；有更新 → Risky，确认后 `add @latest` 重写 spec |
| 更新后插件声明丢了 `dsh.bundle` | CLI reconcile 自动把它移出层栈（不会留僵尸层），日志会显示 warning；UI 无额外处理 |
| 更新要跑构建脚本被 pnpm 拦 | 复用现有 `parseIgnoredBuilds` + `pendingApprove` 放行重试（安装路径已有，零新代码） |
| 更新过程中实例被用户手动启动 | 沿用安装路径现状：`requireStoppedInstance` 只在开始时校验。**明确列为已知限制**，后续可加"操作期间锁定启动按钮" |
| `pnpm-lock.yaml` 损坏 | 只影响本地开发/git 类的信息展示，npm 检查不读 lock，完全不受影响 |
| github 类 | 不给更新按钮（显示"请在目录页重新安装"），服务端也拒绝 update 请求 |
| builtin 类（`dsh-self-mcp`） | **支持重装**：`Runnable=true`，按钮为「更新到 vX」；服务端 `UpdatePlugin` 委派 `reinstallBuiltinSelfRestart`（重新解出内嵌源码 + 常规 pnpm 重装），全程不依赖外网 |

**落地时的偏差与理由**（设计稿写完后才发现的）：

1. **`UpdateCheck.Runnable` 是后加的字段**：最初只在 kind 上判断，导致"能否执行"这一判断散落在前端三处
   （按钮渲染、可更新计数、发现页徽标）。收成一个服务端字段后，前端不需要知道任何 kind 语义。
2. **`Updatable` 只统计 `HasUpdate && Runnable`**：否则 github/builtin 的新版会让总览显示"可更新 N"却一个都点不动。
3. **github 本期 `Runnable=false`**：与 §3.2 的"只检测不执行"一致；UI 是 `git 来源 · 请重新安装` 提示。
   （builtin 后来补上了重装动作，见第 8 条。）
4. **`resolveNpmName` 增加 fallback 参数（依赖 key）**：手工写的 `"pkg": "^1.2.3"`（只有范围没有名字的 spec）
   是合法 npm，但包名只存在于依赖 key 里；不兜底会把这类行误判为"无法识别包名"。这是实际写测试时才暴露的。
5. **`latest` / `*` 视为范围内**：语义上等价于"永远跟最新"，因此走 `pnpm update`，不改写 spec。
6. **发现页不直接更新**：只把 `已安装` 徽标升级成 `可更新 vX`（点击切到已安装页），
   避免把"改用户环境"的动作放进浏览流。
7. **右栏抽屉的开关行为未改动**：更新完成时由 App 的既有逻辑收起抽屉 —— 与安装/卸载完全一致，
   没有为更新新增任何抽屉语义。
8. **builtin 的 `Runnable` 改为 `HasUpdate`（内置插件重装已实现）**：起因是用户反馈"装了插件还是
   打不开内置 DSH 视图、一直验证不通过"。根因是**内置插件没有升级路径**：`UpdatePlugin` 直接拒绝
   builtin、`CheckPluginUpdates` 给 `Runnable=false`、`InstallSelfRestartPlugin` 在"已安装"时
   `Already` 早退（pnpm 那一步被跳过），而 UI 在已装时只给「卸载」——于是装过旧副本（缺
   `relaxEmbedAuth`）的用户永远升不上来，跨源内嵌拿不到 `SameSite=Strict` 会话 cookie → 永久 401。
   现在：`InstallSelfRestartPlugin` 总是重新解出 + 重装（幂等）；`UpdatePlugin` builtin 分支委派
   `reinstallBuiltinSelfRestart`；内置面板在已装时给出「更新到 vX / 重新安装」按钮，并显示
   "已装副本 vX 旧于内置 vY"。⚠️ 配套纪律：**插件能力变更必须 bump `embed/dsh-self-mcp/package.json`
   的版本号**，否则 `pluginCopyMismatchReason` 分辨不出新旧副本。

**已知限制（与设计一致，未修）**：

- 更新期间实例被手动启动：`requireStoppedInstance` 只在操作开始时校验一次；
- 检查更新会随工具条/挂载点触发（首次 8 并发、5 分钟内命中缓存），离线时每行显示"检查失败"而不阻断列表。
